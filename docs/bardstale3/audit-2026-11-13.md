# Bard's Tale 3 (Amiga): codebreaker gap audit, 2026-11-13

Report-only audit, 2026-11-13. None of these corrections have been applied yet.
Run by an independent codebreaker re-derivation: the auditor wrote its own Python decoders (an
independent Huffman decoder and a stock Okumura LZHUF) and compared them against the TypeScript port.
The audit covered Bard's Tale 1-3 together; findings that are family-wide are repeated here so this
page stands alone. Sister pages: `docs/bardstale1/audit-2026-11-13.md`,
`docs/bardstale2/audit-2026-11-13.md`.

Data location used: `data/_unexplored_/BardsTale3/`. The slave identity strings check out.

## Summary verdict

- The picture codec is correct: a textbook Okumura LZHUF reproduces BT3 84/84 records byte-exact, and
  matches the TypeScript port.
- Two open TODO rows (`bt3-slot84`, `bt3-remap-extra-rows`) are wrong. Slot 84 is not corrupt: our own
  decoder throws on a harmless one-byte read-ahead past EOF. **BT3 has 85 real pictures.**
- The BT3 sub-frame XOR is described incorrectly in the prose (the code is right).
- `bt3-monster-banks` rests on a wrong premise (they are raw 48-byte stat records, not graphics), and
  `maps.hi`/`maps.lo` are stock LZHUF, a cheap win.
- **No map, wall or door encoding is claimed anywhere in the BT docs**, so there was nothing to audit
  there; it is untracked.

## Claims confirmed

- Game identity from the slave strings.
- BT3 records decode to a constant 19,712 bytes (4 x 4,928 chunky); holds 85/85 including slot 84.
- The `all.pic` sentinel at `[85]` equals the file length (526,002).
- The `bard3` palette path: `0x2589E` remap -> `0x25A98` select -> `0x25978` palettes. Palette-select
  bytes reach at most 8, and the 9 palettes at `0x25978` end exactly at `0x25A98`, where the select table
  starts.
- BT3 `title`, `titlescreen`, `victory` and `finalBardscreen` are IFF ILBM (FORM/ILBM/BMHD 320x200).
- The code's sub-frame chain XOR (`uncryptXorBard3`, line 571) is correct (see finding 3).

## Claims wrong or overstated

### 1. WRONG: "BT3 `all.pic` slot 84 is corrupt or truncated, and its LZ77 stream runs past EOF"
- **Docs say:** `docs/bardstale-picture-format.md:139,141-157`; TODO row `bt3-slot84`
  (`docs/bardstale3/TODO.md:12`); `docs/bardstale3/amiga/data-structure.md:44-48`; enshrined by the test at
  `tools/shared/__tests__/bardstale-codecs.test.ts:108-113`.
- **Audit found:** an independent stock Okumura LZHUF decoder over all 85 records consumes exactly
  span + 1 bytes on every record (85/85). The extra byte is the decoder refilling its bit buffer while 8
  or fewer bits remain, so it reads one byte past the end of each record. For record 84 that byte is past
  EOF. 15 bits were still buffered at the end, so the phantom byte is never used.
- **Cause:** `readU8` at `bardstale-codecs.ts:45` throws on that refill read. That is a bug in our port,
  not bad data. The same read-ahead is why `loadBard3Picture` checks `at.v - 1` (line 675).
- **Evidence:** slot 84 decodes to 19,712 bytes and renders as 4 clean animation frames (an old bearded
  man with goggles at a machine; row 5 of `bt3_sheet.png`). `bard3`'s remap table also lists picture 84
  (row 87), so the game itself references it.
- **Fix:** BT3 has **85** real pictures. Let the bit refill return 0 at EOF (as Okumura's `getc` does),
  raise `REAL_PICTURE_COUNT` to 85, flip the test, close `bt3-slot84`.

### 2. WRONG: "4 unaccounted-for rows in `bard3`'s 88-row remap table"
- **Docs say:** `picture-format.md:231-233,277`; TODO row `bt3-remap-extra-rows`.
- **Audit found:** the table at `bard3+0x2589E` holds 0-84 once each (85 rows) plus three `0xFF` rows,
  at rows 27, 81 and 86. So it is 3 empty rows plus picture 84, not 4 unknown rows.
- **Fix:** close the row; document `0xFF` as "no picture".

### 3. WRONG: the BT3 sub-frame XOR is described incorrectly
- **Docs say:** `picture-format.md:186-189`: sub-frames 1-3 are each XORed against sub-frame 0, offset
  range 0..4927.
- **Audit found:** the code (`uncryptXorBard3`, line 571) does a running chain over 14,784 bytes, where
  frame n is XORed with the already-decoded frame n-1. The two readings differ on 85/85 records.
  Rendered both: the chain gives clean frames; the doc's version gives noise in frames 2-3
  (`bt3_sheet.png`, rows 2, 4 and 6). The code is right.
- **Fix:** correct the prose.

### 4. WRONG premise: TODO `bt3-monster-banks` ("try `unpackBard3`")
- **Docs say:** TODO:7, `bardstale3/amiga/data-structure.md:24-27`, `picture-format.md:266-270`.
- **Audit found:** `monsterh` and `monsterl` have no size header. All 41 record spans are multiples of
  48. The records are raw 48-byte monster stat entries with high-bit ASCII names ("Red Dragon/\s", "Maze
  Fur/y\ies", "Unbeliever", "Red Eye"). They are not graphics.
- **Fix:** rewrite the row as "decode the 48-byte monster record".

### 5. Cheap win: BT3 `maps.hi` / `maps.lo` are stock LZHUF
- TODO `bt3-maps` lists the content as unknown. All 71 records decode as `[u32 size][LZHUF]` with
  consumption = span + 1 (71/71). Each record starts with a 16-byte high-bit name ("Lucencia", "Celaria
  Bree", "Wilderness", "Tower"), then width and height bytes (0x0C/0x10/0x14), then a table of word
  offsets.
- **Fix:** update the row; the next step is the cell format.

### 6. OVERSTATED: "Structurally the Okumura LZHUF family"
- `picture-format.md:171`. It is exactly stock Okumura LZHUF (N = 4096, F = 60, THRESHOLD = 2, ring
  buffer filled with spaces). A textbook implementation reproduces 84/84 records byte-exact. Say so; it
  gives a third-party oracle.

### 7. OVERSTATED: "the 4 sub-frames are near-identical with small local differences"
- `picture-format.md:190-192`, `bardstale3/amiga/data-structure.md:57-59`. On average 28.6% of bytes
  differ from the previous frame (max 66%). Picture 20 is a zoom-in where the creature grows across the
  frames; picture 3's frame 3 differs by 49%. Reword.

### 8. OVERSTATED / circular: BT3 "0 palette misses"
- `bardstale3/amiga/data-structure.md:51-52`, `picture-format.md:224-226`. `getPictureIndexGame` throws
  when a lookup misses, so the picture would be logged as FAILED. `paletteMisses` only counts all-zero
  palettes, so it can never record a lookup miss, and `DEFAULT_PALETTE` is dead code. The extractor header
  (`bardstale3/export-data.ts:21-23`) also says some indices are missing from the table, which
  contradicts the "0 misses" claim. In fact all 85 are present.

### 9. OVERSTATED: "no count field; counts must be found by decode-until-failure"
- `picture-format.md:36-43,127-133`. The first directory offset divided by 4 gives the slot count
  directly (344/4 = 86 for BT3, consistent with 85 pictures plus the sentinel at `[85]`). The
  "not decisive" paths-tried entry is wrong; the directory scan was decisive.
