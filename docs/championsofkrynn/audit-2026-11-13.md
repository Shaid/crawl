## Summary verdict

- Container, GEO, ECL bindings and the DAA pixel payload are solid; the DAA payload is now
  oracle-confirmed against the DOS DAX at 100%.
- The wall-palette claim (DUNGCOM.DAA entries 16-31) is wrong-likely: the oracle says entries 0-15
  (the shared EGA default palette).
- The flat whole-file wall-tile bank "fits 115/115" has no null control and scores near the null on
  a seam test.
- `8X8D1.DAX` is not headerless 1bpp; it is a headered 4bpp tile bank, and is the pixel oracle for
  the DAA decode.
- Biggest risk: SPRIT/PIC `.DAA` banks (monster sprites, location pictures) use a third container
  shape that the shipped reader parses as 0 OK, and no TODO row covers it.

## Claims confirmed

| Claim | Evidence the audit used |
|---|---|
| DAX container | 239/239 entries exact rawSize, chain and EOF. |
| BE DAA container, on the files it fits | `8X8D0.DAA` and `8X8D1.DAA` are byte-identical; id 201's compressed span is 1341/1341 zero bytes. |

## Claims wrong or overstated

### 1. WRONG-likely: Champions wall palette = DUNGCOM.DAA entries 16-31

- **Docs say.** Uncommitted correction, `data-structure.md:190-294`; `readChampionsWallPalette`; TODO
  row `cok-8x8ddaa-palette-mechanism`.
- **Audit found.**
  - (a) *False premise.* "DUNGCOM.DAA byte-identical to BORDER.DAA (287 B)" is false: the files are
    287 B and 8,935 B and differ at byte 3; only their embedded palettes match. Champions'
    `BORDER.DAA` is byte-identical to Death Knights' `BORDER.DAA`.
  - (b) *The precedent does not discriminate.* The Death Knights palette upper half (16-31) is
    identical in every Death Knights file (BACK1, BIGPIC1, COMSPR, CPIC1, WILDCOM, DUNGCOM, `8x8d1`
    id 202), so it says nothing specific about DUNGCOM.
  - (c) *The mechanism is in Death Knights' data.* Its 5-plane tiles hold only pixel value 0 or
    16-31 (histogram over all entries: 27,089 zeros and 0 hits in 1-15). Plane 5 itself selects the
    upper half, so the "missing register-offset mechanism" was never needed.
  - (d) *Decisive oracle.* Champions' own DOS-format `8X8D1.DAX` holds the same tiles as EGA 4bpp
    nibbles. Amiga DAA pixel indices equal the DOS nibbles under the identity mapping: 100% for ids
    11 and 23 (70 tiles each) and 202 (38 tiles); 99.97% for id 203. The DOS game displays these
    with the EGA default palette, which is exactly Champions' shared entries 0-15
    (`000 00a 0a0 0aa a00 a0a a50 aaa 555 55f 5f5 5ff f55 f5f ff5 fff`).
- **Fix.** Switch to entries 0-15, label it "DOS-index-identical", and reframe the TODO row from
  "mechanism" to verifying against a screenshot.

### 2. WRONG/UNSUPPORTED: addressing model "flat whole-file bank fits 115/115"

- **Docs say.** `data-structure.md:162-188, 315`; the daa-tiles module doc.
- **Audit found.**
  - No null control: an in-range test against a bank of 700+ tiles cannot fail.
  - Seam oracle (how often pixels match across adjacent tile edges): the shipped flat bank sits near
    the null for every wall, 0.23-0.50 versus 0.16-0.34 for random tiles. The per-wall model (blank,
    45 universal tiles from 203, then entry `10W+1` and `10W+2`, or entry `W` for 5-slice walls)
    scores 0.39-0.68. For calibration, Death Knights' quarters model scores 0.51-0.71 against a
    0.17-0.30 null, so 0.39-0.68 is in the "probably right" band.
  - Structural fit: 5-slice walldefs index only 1-115, which is 45 + 70. The entries line up with
    10-slice walldef ids exactly: {1,3,5,8} <-> {11/12, 31/32, 51/52, 81/82}, {19,21,15,17} <->
    {191/192, 211/212, 151/152, 171/172}, and 5-slice ids <-> themselves.
  - Code/doc contradiction: the code gives bank 2 no universal prefix, while the module doc
    (`goldbox-daa-tiles.ts:147`) says it reuses bank 1's id 203. Yet bank-2 walls do index 1-45.
- **Unexplained part.** Indices 186-236, used only by the second group of 10-slice walls.
- **Fix.** Downgrade to "wrong (seam ~ null)". Open `cok-wall-addressing` with the seam oracle as
  the test. A fair re-codebreaker target once 186+ is the only unknown.

### 3. WRONG: "`8X8D1.DAX` tiles CONFIRMED, headerless 1bpp"

- **Docs say.** `data-structure.md:68-91, 355`.
- **Audit found.** Each entry is a 9-byte LE header, an 8-byte EGA-to-CGA nibble map, then 32 B per
  4bpp tile. 2257 = 17 + 70*32, matching the DAA tile counts. The "crenellation" render was a
  misread.
- **Upside.** This file is the pixel oracle that confirms the DAA decode (finding 1d).

### 4. WRONG/UNTRACKED: SPRIT and PIC `.DAA` banks are not the BE DAA container

- Champions SPRIT1/2 and pic1/2 parse as 0 OK under the shipped `readAmigaDaaDirectory`. They use a
  third directory shape: a u16 BE header length, then 6-byte entries `{id u8, 0 u8, offset u32 BE}`
  with no sizes. That fits 7/7 files (across Champions and Death Knights): remainder 0, offsets
  monotonic, pad byte always 0. Block payloads start `00 xx 03 00 58 00 0b fc ...`.
- Monster sprites and location pictures are the largest undecoded asset class and no TODO row covers
  them. `globals.daa` and `pointers.daa` (no directory) are also untracked.
- **Fix.** Add row `cok-sprit-pic-container`.

### 5. Contradictions within docs and code

- Champions `data-structure.md`: lines 317-322, 359 and 362 still say "palette OPEN / synthetic
  greyscale", contradicting the uncommitted correction; lines 352-355 call the 8X8D1.DAX path
  CONFIRMED; line 344 attributes `{19,20,255}` to bank 1 (it is bank 2).
- `goldbox-daa-tiles.ts`: line 151 says "9/9 WALLDEF1 ids" (WALLDEF1 has 6); line 257 references
  `CHAMPIONS_WALL_PALETTE_FALLBACK`, which is defined nowhere.
- Champions export namespaces the sentinels (1255, 2127).
- Champions ECL: the unknown-opcode ratio is 0.18-0.24%, not 0. Read the Champions exe's own operand
  table, as done for Dark Queen (see `docs/darkqueenofkrynn/audit-2026-11-13.md`).

## Unverified / open

## Recommended corrections, cheapest/highest value first

1. Switch the Champions palette to entries 0-15 (finding 1).
2. Fix the stale/contradictory doc text and the two code references (finding 5).
3. Downgrade the flat-bank claim and open `cok-wall-addressing` (finding 2).
4. Re-describe `8X8D1.DAX` as headered 4bpp and use it as the standing pixel oracle (finding 3).
5. Open `cok-sprit-pic-container` (finding 4).
6. Run the seam oracle as a null-controlled gate in the shared decoders.
