# Might & Magic 1 (DOS): codebreaker gap audit, 2026-11-13

Report-only audit, 2026-11-13. None of these corrections have been applied yet.
Run by an independent codebreaker re-derivation of the MM1, MM2 and MM3 data and walker claims. The
audit fetched two outside oracles as references: ScummVM `engines/mm/mm1` (`maps/maps.{h,cpp}`,
`maps/map.{h,cpp}`, `game/view_base.cpp`, `views/game_view.cpp`, `maps/mapNN.h`) and Vairn/MM2
(`21-map-dat-format.md`, `tools/mm2_map_move.py`, `game/src/gameplay/Movement.cpp`,
`EXTRACTED/decomp/mm2_map_codec.h`, `mm2_attrib_codec.c`). Findings shared with MM2/MM3 are repeated
here so the page stands alone. Sister pages: `docs/mm2/audit-2026-11-13.md`,
`docs/mm3/audit-2026-11-13.md`.

## Summary verdict

- The MM1 data decodes are sound (MAZEDATA, `.OVR` size invariant, overland exit grid), but the MM1
  walker is wrong in ways the user would notice in play. In order of impact:
  1. Wall art is chosen by view depth; the game chooses it by wall code (every wall one step away shows a
     door, every wall two steps away a torch).
  2. Edges never cross: the real game wraps indoor maps and links the 20 overland sectors.
  3. The walker also checks the destination cell's back wall; the game does not (about 1% of indoor moves
     wrongly blocked).
  4. MM1 borrows MM2's screen geometry.
  5. Start positions are a heuristic.
- The N/E/S/W labels in the MM1 docs and codecs are a permutation of the real layout.
- Biggest risk: doc claims are "verified-real" against Vairn's prose or a rendering predicate, not
  against the game.

## Claims confirmed

- **MM1 `MAZEDATA.DTA`:** 55 x 512 bytes. Layout row-major `y*16+x` with y+1 = north (ScummVM agrees).
  Walls are symmetric between neighbours (99.9%).
- **MM1 overland exit grid:** 62/62 links reciprocal; the `.OVR` `14 + code + data` size invariant holds.
- **Frustum engine orientation and `movementBlocked`'s current-cell bit:** both match ScummVM DIRMASK and
  the `0x55` mask exactly.
- **Wall-code meaning:** 2 = door and 3 = torch, confirmed by ScummVM's `WallType` enum and by the WALLPIX
  art.
- **Bit layout correction itself is spot-checked in the main session:** wall-bit labels are W,S,E,N
  (97% neighbour agreement vs 37%).

## Claims wrong or overstated

### 1. WRONG: MM1 picks its WALLPIX set by view depth; the game picks it by wall code
- **Docs say:** the three `.OVR` wall fields (`MAP_2/4/6`, exported as `wallEntries[0..2]`) are "near/mid/far
  frustum depth lanes": `docs/walker-mm.md:21`, `docs/mm1/dosega/data-structure.md:383`,
  `tools/walker/games-mm.ts:96-97` and `:425-428` (`wallLaneForDepth`). Related: "MM1 renders no torch
  overlay ... WALLPIX has no torch frames / no door/torch art": `docs/walker-mm.md:22`,
  `games-mm.ts:460-462`, `tools/walker-mm/maze3d.ts:418-423`.
- **Audit found:** ScummVM `views/game_view.cpp` `GameView::drawTile()` picks `section = 0` when
  `(mask & 0x55) == mask` (code 1), `1` when the `0x55` check fails but the `0xaa` check passes (code 2),
  and `2` otherwise (code 3), then uses `maps._tiles[section]`, which `loadTiles()` fills from `MAP_2`,
  `MAP_4`, `MAP_6` in that order. `ViewBase::forward` uses the same code->offset rule to read
  `MAP_30+offset` for its "can't swim" check.
- **Bytes check:** the front slice of WALLPIX entries 0, 1, 2 (Sorpigal's `wallEntries = [0,1,2]`,
  rendered as `wallpix012.png`): entry 0 plain brick wall, entry 1 a wooden door between two torches,
  entry 2 a wall with one torch.
- **Effect:** for all 55 screens, depth 0 always uses the code-1 art, depth 1 the door art, depth 2+ the
  torch art, whatever the real wall code is: 1,349 door faces and 1,469 torch faces indoors. On overland
  screens the codes select biomes (trees, mountains, water), scrambled the same way.
- **Spot-checked in the main session:** `games-mm.ts:427` `wallLaneForDepth` picks MM1 wall art by depth.
- **Fix:** correct both docs and the code comments. Codes 1/2/3 select `MAP_2/MAP_4/MAP_6`; MM1 does have
  door and torch art. One-line logic change in the walker.

### 2. WRONG: "MM1 cross-screen stepping: none (edges clamp)"
- **Docs say:** `docs/walker-mm.md:25`; `neighbors: [-1,-1,-1,-1]` at `games-mm.ts:167`.
- **Audit found:** ScummVM `Maps::step()` reads the N/E/S/W exit `(u16 id, section)` from data-segment
  offsets 8/11/14/17. Our MM1 data doc already documents these at `data-structure.md:384-387`, so this is
  a doc-vs-code contradiction. Resolving every exit in the 55 retail `.OVR` files with ScummVM's
  `getIndex` rules (`LOOKUPS_START = {0,0,14,34}` plus each map's id from its `MapNN` constructor):
  - Every indoor map's four exits point back to itself, so walking off an edge wraps around.
  - The 20 overland sectors (`areaa1`..`areae4`, screens 14-33) form a reciprocal 5x4 grid: **62/62 links
    reciprocal**; outer edges point back to the sector itself.
  - Only exception: `pp2`, whose exits all go to `dragad` (44).
- **Spot-checked in the main session:** `neighbors: [-1,-1,-1,-1]` at `games-mm.ts:167`.
- **Code still exports the retracted guess:** `scripts/mm1lib/ovr.py:26` and `:71-73` describe these bytes
  as "4x 3-byte event records (x, y, kind)"; `scripts/extract_mm1_ovr.py:104` exports them as
  `eventTriples`. This was retracted at `data-structure.md:408-415`.
- **Fix:** rename `eventTriples` to `exits[{id, section, screen}]`, resolve them in the exporter, wire into
  MM1 `neighbors`, fix the walker doc row.

### 3. WRONG: the walker also checks the destination cell's back wall (MM1 and MM2)
- **Walker:** `maze3d.ts:100-102` blocks a move if the destination cell's collision bit facing back toward
  you is set (from Vairn's `mm2_map_move.py` helper).
- **Game:** looks only at the current cell. MM1 (ScummVM `ViewBase::forward`): `_currentState & 0x55 &
  mask`.
- The data really is asymmetric: in MM1, 121 door faces are open on one side and blocked on the other (160
  in MM2), matching `Map::unlockDoor` toggling the current cell's bit.
- **Effect:** the walker blocks moves the game allows: MM1 356 of 33,600 indoor moves (1.1%) plus 28
  overland; no cases the other way.
- **Fix:** drop the back-face check; document the current-cell-only rule as confirmed.

### 4. OVERSTATED: "MM1 and MM2 share this frustum math"
- **Docs say:** `maze3d.ts:1-8`, `games-mm.ts:5-8`.
- **Audit found:** ScummVM's MM1 `GameView::drawScene()` differs from the MM2 engine:
  - walks 4 depths and stops at the first front wall;
  - a neighbour's forward wall is a **crop of the front tile** (`ARR19` with `srcLeft/srcWidth`), not a
    mirrored side slice;
  - positions differ: left x = `ARR7x4` = 0/32/72/96 and front x = `ARR11x4` = 32/72/96/112, whereas the
    walker uses MM2's `frontX` 32/64/88/104;
  - draws **nothing** when the map or cell is dark (`if (!_isDark) drawScene()`).
- The walker's `wallpixSliceName` maps the mirrored bases 12-15 to `left0`/`left1`, a related
  approximation.
- **Fix:** call MM1 rendering an approximation; cheap fix is to port `drawScene` from ScummVM's
  `ARR1..ARR19`.

### 5. WRONG: start positions
- **Docs say:** `docs/walker-mm.md:90` says Sorpigal renders at "entry cell (4,2), matching the OVR data".
- **Audit found:** both (4,2) and `maps.json` `entry` come from the first-fully-open-cell heuristic
  (`tools/mm1/map.ts:160-172`); no OVR field gives it. Real starts from ScummVM `Maps::loadTown`:

  | Town | Start cell | Facing |
  |---|---|---|
  | Sorpigal | (8,3) | N |
  | Portsmith | (3,12) | W |
  | Algary | (14,8) | W |
  | Dusk | (11,8) | E |
  | Erliquin | (4,4) | N |

- **Fix:** start from the town table; fix line 90.

### 6. WRONG in docs and codecs (harmless in the walker): N/E/S/W bit labels, map pages 0 and 1
- **Docs say:** `N = byte&3, E = >>2, S = >>4, W = >>6`, and "West has no dark slot; 0x80 = event":
  `docs/mm1/dosega/data-structure.md:22-42`, `tools/mm1/map.ts:14-17` (and MM2 equivalents). The labels
  come from Vairn's own prose, so "verified-real" means it matched his prose, not the game.
- **Audit found:** symmetry across neighbouring cells: bits 4-5 of a cell match bits 0-1 of cell x+1 on
  6,996/7,005 faces; bits 6-7 match bits 2-3 of cell y+1 on 7,150/7,160. Actual layout: **bits 0-1 W, 2-3
  S, 4-5 E, 6-7 N**, y+1 = north, `idx = y*16+x`. ScummVM confirms: `DIRMASK_N = 0xC0, E = 0x30, S = 0x0C,
  W = 0x03`, `getMoveDelta` S = (0,-1). Vairn's decomp agrees: `mm2_map_facing_shift` gives N = 6, with a
  comment that facing "N actually reads the file's WEST slot". MM3 maze nibbles use the same W,S,E,N order.
- **Collision page (per ScummVM):** wall bits are `0x55` & dirmask: N 0x40, E 0x10, S 0x04, W 0x01.
  `0x20` is a **cell-level dark** flag (`CELL_DARK = 0x20`; Vairn `btst #5` @ `0x53DC`). `0x80` marks a
  special/event cell. `0x02` and `0x08` are unidentified, not "per-direction dark".
- The frustum engine and `movementBlocked` already use the correct order (they repack bytes unchanged),
  but every consumer of the exported `cell.visual.n/e/s/w` names is mislabelled. MM1's `export-maps.ts:49`
  `cellIsDark` scores TP 160, **FP 1,757**, FN 100 against `0x20`.
- **Spot-checked in the main session:** W,S,E,N (97% vs 37% agreement).
- **Fix:** relabel the decoded fields; add a `> Correction:` block to the data-structure doc and codecs;
  make `dark` the `0x20` bit; add a TODO row for `0x02`/`0x08`.
