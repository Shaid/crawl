# Lands of Lore (DOS VGA): gap audit, 2026-11-13

> Changes applied: [audit-2026-11-13-changes.md](audit-2026-11-13-changes.md)

Report-only audit, 2026-11-13. None of these corrections have been applied yet. It was run by an
independent codebreaker re-derivation over the Westwood/SSI family (own LCW and PAK parsers in fresh
Python; current ScummVM master sources were fetched for cross-references). This page carries the
findings that touch Lands of Lore. Sibling pages: `docs/eotb/audit-2026-11-13.md`,
`docs/eotb2/audit-2026-11-13.md`, `docs/eotb3/audit-2026-11-13.md`,
`docs/dungeonhack/audit-2026-11-13.md`.

## Summary verdict

- CMZ and VCN/VMP structure hold up.
- The `.WLL` claims are wrong: wallTypeIndex does not increment cleanly 0..51, duplicate keys occur,
  and the "zero misses" fallback is exercised on 2 of the 11 exported levels.
- The TODO uses non-allowed statuses and a stale row.
- Biggest risk: the walker draws solid walls for raw CMZ values with no `.WLL` record on levels 2 and
  3; some of these may be script-driven cells.

## Claims confirmed

| Claim | Evidence the audit used |
|---|---|
| CMZ | 4102 = 6 + 32x32x4 for LoL CMZ levels 1-12 after decompression. |
| VCN/VMP | LoL with `vcnShift`+128+384: decompressed sizes tile exactly; VMP max tile index = `numTiles-1`. LoL VMP counts are 330 + N x 431 with N = 2-6. |

## Claims wrong or overstated

### 1. WRONG: `.WLL` "wallTypeIndex increments cleanly 0..51" and "fallback unexercised"

- **Docs say.** `docs/landsoflore/dosvga/data-structure.md`, section WLL: indices increment cleanly
  0..51. The `lol-wll-mapping-fallback` row says zero misses (LEVEL1 only).
  `tools/landsoflore/decode-wll.ts:61` comment: "(unobserved) duplicate key".
- **Audit found.**
  - `LEVEL1.WLL` indices run 0-26, then 66, 67, 53, 54, 55, 57, ... (not sequential). Only LEVEL12 is
    sequential.
  - `LEVEL2.WLL` redefines indices 1 and 2, so duplicate keys do occur.
  - Raw CMZ values with no `.WLL` record: L2 has 12 values (`46, 53-57, 59, 60...`, about 30 sides)
    and L3 has 5 values (20 sides). Levels 1 and 4-12 have none.
  - For those, `view-model.ts:37`'s fallback (`raw<=max ? raw : 1`) draws a solid wall.
  - `olol_setWallType` (`script_lol.cpp:95`) can rewrite wall bytes at runtime, so these may be
    script-driven cells.
- **Verdict.** WRONG on "sequential" and "unobserved". The fallback is exercised on 2 of the 11
  exported levels.
- **Fix.** Correct the WLL section; re-open the fallback row (it is marked `closed` while still in the
  TODO table); check the `LEVEL2.INI`/`LEVEL3.INI` EMC2 bytecode for `setWallType` targets (run the
  existing `decode-emc.ts` on them and grep for `olol_setWallType`).

### 2. TODO hygiene and stale status

- The LoL TODO has a row with status `closed` and one with `narrowed`, neither an allowed status.
- `lol-iso-remaining-paks` says L02-L29 are not pulled, but `build/cache/landsoflore/iso/DATA` holds
  L01-L12 and the exporter ships 11 levels (`export-dungeon.ts:83-85`; L10 is skipped).

## Unverified / open

- Whether the L2/L3 unmapped raw values are set by script at runtime (`olol_setWallType`); the
  EMC2 bytecode has not been examined.
- Why L10 is skipped by the exporter was not investigated.

## Recommended corrections, cheapest/highest value first

1. Run `decode-emc.ts` over `LEVEL2.INI`/`LEVEL3.INI` and grep for `olol_setWallType` (finding 1).
2. Correct the WLL section and re-open `lol-wll-mapping-fallback`.
3. Fix the TODO statuses and the `lol-iso-remaining-paks` row (finding 2).
