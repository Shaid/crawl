`data/ssi/DarkQueenOfKrynn/data/Disk1-3`; all five Krynn/Savage titles live under `data/ssi/`.

## Summary verdict

- The headline claim "no first-person wall-art compositing mechanism" is wrong. The exe's own ECL
  operand table decodes cleanly, wallsets load via `0x21` "LOAD FILES", and the wall art exists as
  pre-scaled TILE containers.
- The "variable GEO CONFIRMED, plane semantics unchanged 98.8%/82.4%" claim hid an 8/20-level
  failure: the exported grid is transposed or scrambled for every non-square level.
- Several docs/TODO contradictions remain, and the TODO carries session-history narrative.
- Biggest risk: the wrong "final verdict" has already steered the extractor and TODO.

## Claims confirmed

- GEO agrees with the new wall-art finding: 19/20 Dark Queen levels use wall types across all three
  5-slice slot ranges (max type 15).
- (Family) DAX container solid on the sibling titles (Champions 239/239, Death Knights 199/199);
  the audit did not report a separate Dark Queen DAX count.

## Claims wrong or overstated

### 1. WRONG: "no first-person wall-art compositing mechanism"

- **Docs say.** `darkqueenofkrynn/amiga/data-structure.md:183-199`, `TODO.md:43-51`, and an extractor
  comment in `export-data.ts`.
- **Audit found.** It decoded the exe's own ECL operand-count jump table (CODE hunk at file +40,
  table at CODE+0x13e64 as the doc cites). It is the v1.3 table, so wallsets load via `0x21`
  "LOAD FILES" as in Pools of Darkness; the doc only ever tested `0x37`. It matches
  `OPCODE_TABLE_POOLS_V13` on every fixed-length opcode. The one difference: `0x31` shares the
  ON GOTO / HORIZONTAL MENU variable-length handler.
- **ECL result.** v1.3 plus `0x31={n:0,dynamicTailHeadCount:2}`, with `0x21` in fill-all mode, gives
  0 unknown / 0 desync over 36,829 visited instructions. 19/20 levels resolve to wallset ids 1-6;
  geo 26 resolves to the 255 sentinel.
- **Null controls.** The v1.1 table gives a 5.0% unknown ratio; stock v1.3 gives 0.72% (247 unknown).
- **The art exists.** Each block of `Disk2/8X8DB.TLB` (ids 1-9) and `8X8DC.TLB` (ids 10-17) is a
  compressed TILE container of 48 pre-scaled sub-images. Every one fits
  `len = 8 + h x widthBytes x (5 + (flag&1))`, from an 8-byte header with h at +0, widthBytes at +6
  and flags at +7: 799/799. The flag-`e0` cases are the 5-plane ones. Rendered greyscale
  (`dqk_sheet.png`), they show 56x56 cobblestone, brick and cave-rock wall faces and a doorway with
  steps.
- **Fix.** Retract section 3's "Final verdict" and the TODO narrative. Add the exe-derived table and
  `eclPath`/`wallsetLoad 0x21` to the extractor. Open row `dqok-wallpiece-render`: map the 48
  sub-images to views/distances and confirm the plane order (sequential 5 planes renders cleanly).

### 2. WRONG: variable GEO "CONFIRMED, plane semantics unchanged 98.8%/82.4%"

- **Docs say.** `data-structure.md:73-82`; `goldbox-glib-format.md:432-444`.
- **Audit found.** For every non-square level the exported grid is transposed or scrambled. Swapping
  width/height raises vertical wall-adjacency agreement:

  | Level | Before | After swap |
  |---|---|---|
  | L18 | 0.093 | 1.0 |
  | L66 | 0.064 | 0.844 |
  | L14 | 0.304 | 0.998 |
  | L38 | 0.213 | 0.992 |
  | L22 | 0.395 | 1.0 |
  | L47 | 0.513 | 1.0 |
  | L54 | 0.436 | 0.92 |

  The 82.4% average hid an 8/20-level failure. Also wrong: "dims ~8x8 to 24x20"; real dimensions run
  from 10x10 to 39x20, plus 22x34, 27x29 and 28x28.
- **Fix.** The header is (height, width) or the planes are column-major. Fix
  `decodeVariableGeoRecord` and re-run the oracle per level, not as an average.
