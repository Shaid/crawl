# Eye of the Beholder 2 (DOS and Amiga): gap audit, 2026-11-13

> Changes applied: [audit-2026-11-13-changes.md](audit-2026-11-13-changes.md)

Report-only audit, 2026-11-13. None of these corrections have been applied yet. It was run by an
independent codebreaker re-derivation over the Westwood/SSI family (own LCW, PAK and AESOP RES
parsers in fresh Python; kyralib and eotb3lib were not imported; current ScummVM master sources
were fetched for cross-references). This page carries the findings that touch EOB2. Sibling pages:
`docs/eotb/audit-2026-11-13.md`, `docs/eotb3/audit-2026-11-13.md`,
`docs/dungeonhack/audit-2026-11-13.md`, `docs/landsoflore/audit-2026-11-13.md`.

## Summary verdict

- MAZ, VCN/VMP size tiling, decoration `.DEC` tiling and the Amiga-versus-DOS identities are solid.
- Wall-decoration rects are read in pixels but stored in 8-pixel columns: the EOB2 DOS and Amiga
  walkers draw every wall decoration at one-eighth width.
- Sub-levels are cumulative wall-mapping layers, not just monster slots; the walker models only sub 0
  and the TODO row understates this.
- "LEVEL15.INF -> level14.maz is Amiga-only" is wrong; DOS reuses it too.
- Biggest risk: an unmodelled reachable game state (sub-level 1) on six levels.

## Claims confirmed

| Claim | Evidence the audit used |
|---|---|
| MAZ | 4102 = 6 + 32x32x4 (header 32,32,4) for all 15 EOB2 levels, both ports; zero trailing data (all 27 EOB1+EOB2 levels). |
| VCN/VMP | EOB2 DOS and Amiga LCW: decompressed sizes tile exactly; VMP max tile index = `numTiles-1`. EOB2 Amiga VMP is little-endian (as both DOS versions). |
| `ITEM.DAT` / `ITEMTYPE.DAT` | EOB2 Amiga is exactly the DOS file byte-swapped, at u16 fields +6/+8/+10 (items) and +0/+2/+14 (types), 0 mismatches. |
| Decoration `.DEC` files | Tile to EOF with 0 residue; max shape index = rect count - 1; flags only {0,1,4,5}. |
| Amiga identities | `.DEC`/`.DCR` are md5-identical to DOS; `TEXT`/`TEXT2`/`TEXT4.CPS` decompress to DOS `TEXT.DAT` exactly. |
| MAZ cross-port | All 15 EOB2 levels byte-identical across ports. |
| `resetWallData` defaults | Match `scene_eob.cpp:542-548`. |
| INF chain mechanism | `initLevelData` (`scene_eob.cpp:155-163`) walks `pos = data + READ_LE_UINT16(pos)` with `data = page+2`, exactly matching the chain kyralib derived empirically (now source-confirmed). |

## Claims wrong or overstated

### 1. WRONG: wall-decoration rects in pixels instead of 8-pixel columns

- **Docs/code say.** `tools/eotb/decode-decorations.ts:45` ("pixel coordinates ... 320x200 canvas");
  `tools/eotb/renderer.ts:66-74`; blits at `tools/eotb/renderer.ts:261,272,274` and
  `tools/eotb2/renderer.ts:172-174`. Verification cited: "193 px, bbox (65,32)-(73,56), 9x25px".
- **Audit found.** ScummVM `Screen_EoB::encodeShape` (`graphics/screen_eob.cpp:629`):
  `src = page + y*320 + (x << 3)`, `w <<= 3`; called with the raw rect at `scene_eob.cpp:508`. Across
  11 files and 1,615 rects (5 EOB1 `.DAT` plus 6 EOB2 `.DEC`, DOS and Amiga) the maximum `x+w` is
  exactly 40 in 10 files and 39 in one (40 = 320/8). BRICK rects 0-2 `(0,55,9,25)`, `(9,55,6,17)`,
  `(15,55,4,11)` sit edge-to-edge in column units. Null-controlled coverage on 9 DOS VGA sheets:
  x8 reading 0.90-1.00, pixel reading 0.12-0.23 (AZURE2 exception, 0.74). The "pixel-exact"
  verification was circular.
- **Fix.** Multiply `x` and `w` by 8 in `decode-decorations.ts` or at the blit; add `> **Correction:**`
  blocks in the EOB2 DOS/Amiga docs (and the EOB1 doc); add row `eotb-dec-rect-units` to
  `docs/eotb2/TODO.md` (and `docs/eotb/TODO.md`). One EOB2 `CRIMSON.DEC` rect, #152 `(5,178,6,27)`,
  runs past row 200 (to y+h=205); handle defensively.

### 2. UNVERIFIED and untracked: sub-levels are cumulative wall-mapping layers

- **Docs say.** `tools/eotb2/decode-inf.ts` is scoped to sub 0. TODO row
  `eotb2-dos-inf-sublevel-decoration-coverage` frames it as "unknown whether real decoration
  assignments exist only in later sub-levels". `scripts/kyralib/inf.py:72-86` says the chain mechanism
  was "derived directly from real bytes (not from source)".
- **Source.** `scene_eob.cpp:35-53`: `loadLevel(level, sub)` calls `resetWallData()` then
  `for (i=0; i<=sub; i++) initLevelData(i)`, so sub-levels stack. `sub` comes from the level-change
  script opcode's operand (`script_eob.cpp:1288-1319`, `loadLevel(index, cmd)`), so sub-level 1 is a
  reachable state.
- **Bytes.** Every block parsed fully; DOS and Amiga identical. Six levels (1, 3, 7, 8, 11, 16) have a
  second block carrying 5-24 wall-mapping records each, plus extra decoration loads (`brown3` on
  level 3, `crimson2` on level 16). On level 3, six of the 16 wall indices both blocks map are mapped
  differently in sub-level 1.
- **MAZ values unmapped in sub 0:**

  | Level | Raw wall values not mapped by sub 0 (sides affected) | Covered by sub 1? |
  |---|---|---|
  | 1 | 59, 63 (24 sides) | Yes |
  | 3 | 61, 62, 64, 67 (55 sides) | Yes |
  | 7 | 64, 65 (16 sides) | Yes |
  | 16 | 53 (1 side) | Yes |
  | 5 (`level5.maz`, shared with level 6) | 14 values, ~100 sides | No, only LEVEL6.INF maps them |

  The walker shows these as "no wall". That matches the engine for sub 0 but is wrong for the sub-1
  entry state.
- **Verdict.** Sub 0 in the walker is faithful as far as it goes; a second real state is unmodelled
  and the TODO row understates it.
- **Fix.** Rewrite that row's question to cover the cumulative wall/decoration layer, cite the source
  lines, add a row for the LEVEL5-vs-LEVEL6 `level5.maz` mapping gap, and add sub-level selection to
  the EOB2 exporter (export sub 0 and sub 0+1 wall maps per level).

### 3. WRONG: "LEVEL15.INF -> level14.maz is Amiga-only"

- **Docs say.** `docs/eotb2/amiga/data-structure.md:266-276`, `:469`; `docs/eotb2/TODO.md:77-78`:
  "DOS's own LEVEL15 uses its own level15.maz".
- **Audit found.** DOS `LEVEL15.INF` decompressed, block at offset 4, has `mazStem` = `level14.maz`
  and wall set `crimson`, identical to the Amiga file. No INF in either port names `level15.maz`
  except LEVEL16. The reuse chain is the same on both ports: LEVEL6->5, LEVEL14->12, LEVEL15->14,
  LEVEL16->15.
- **Fix.** Correction block in the Amiga doc; fix the DOS doc's maze-reuse list (missing 15->14).

### 4. Related claims shared with EOB1

The `VMP identical across wall sets` claim (EOB1 doc `:367`) is false for EOB2 too (all 20 `.VMP`
files across EOB1 and EOB2 have distinct md5s), and the `skip=true` prefix theory is wrong (applies
to the shared loader). See `docs/eotb/audit-2026-11-13.md` for details.
