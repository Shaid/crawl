# Eye of the Beholder 3 (DOS VGA): gap audit, 2026-11-13

> Changes applied: [audit-2026-11-13-changes.md](audit-2026-11-13-changes.md)

Report-only audit, 2026-11-13. None of these corrections have been applied yet. It was run by an
independent codebreaker re-derivation over the Westwood/SSI family (own LCW, PAK and AESOP RES
parsers in fresh Python; kyralib and eotb3lib were not imported; current ScummVM master sources
were fetched for cross-references). This page carries the findings that touch EOB3. Sibling pages:
`docs/eotb/audit-2026-11-13.md`, `docs/eotb2/audit-2026-11-13.md`,
`docs/dungeonhack/audit-2026-11-13.md`, `docs/landsoflore/audit-2026-11-13.md`.

## Summary verdict

- The `ITEMTYPE.DAT` "2-byte offset correction to ThirdEye" is a framing error: ThirdEye was right.
  The EOB3 decoder labels every field wrongly, though the numeric values come out right.
- `EYE.RES` has 2,399,876 bytes (35%) not covered by any directory entry while its header says
  `lost_space=0`; "container confirmed" was never tiling-checked.
- The EOB3 `CHARGEN` item tables are EOB2's files verbatim.
- Biggest risk: a wrong "correction" of a correct external source has been written into docs and
  `itemdat.py`.

## Claims confirmed

| Claim | Evidence the audit used |

| Item data identity | `data/eotb3/dosvga/CHARGEN/ITEMTYPE.DAT` and `ITEM.DAT` are md5-identical to `data/eotb2/dosvga/ITEMTYPE.DAT` and `ITEM.DAT`. |

## Claims wrong or overstated

### 1. WRONG: EOB3 `ITEMTYPE.DAT` "2-byte offset correction to ThirdEye"

- **Docs say.** `docs/eotb3/itemtype-dat-offset-correction.md`: no count header, trailing `u16` =
  `0x0004`, every field 2 bytes later than ThirdEye documents; `mask_A`, `mask_B`, `field3` at
  +0/+2/+4 unknown. The same reading is in `docs/eotb3/dosvga/data-structure.md` section 6.2 and
  `scripts/eotb3lib/itemdat.py:32-51`.
- **Audit found.**
  - The first `u16` of `ITEMTYPE.DAT` is 64, the record count. The file is 1026 B = 2 + 64x16.
  - The "trailer" `0x0004` is the last record's `extraProperties` (true offset +14).
  - ScummVM `items_eob.cpp:109-121` gives the true record layout: `invFlags` u16 at +0, `handFlags`
    u16 at +2, `armorClass` s8 at +4, `allowedClasses` at +5, `requiredHands` at +6, damage dice from
    +7. That is ThirdEye's layout.
  - The EOB3 decoder reads records from file offset 0 instead of 2. Its "+6 AC" therefore lands on the
    true +4, so the values come out right but every label is misassigned: `mask_A` is the previous
    record's `extraProperties` (for record 0 it is the count), and `field3` is `handFlags`.
  - The doc says the same format applies to Dungeon Hack, but no `ITEMTYPE.DAT` exists in
    `data/dungeonhack`.
- **Verdict.** WRONG, presented as a correction of a correct external source.
- **Fix.** Supersede the correction doc with a `> **Correction:**` block; re-label the fields in
  section 6.2 and `itemdat.py`; note that the EOB3 `CHARGEN` item tables are EOB2's files verbatim
  (probably for party import) and link to the EOB2 spec; drop the Dungeon Hack claim.

### 2. OVERSTATED / UNTRACKED: `EYE.RES` "container confirmed"

- **Audit found.** For `HACK.RES` and `OPEN.RES` (Dungeon Hack), the bytes not covered by any
  directory entry equal the header's `lost_space` exactly (45,816 and 12,588): a solid tiling result.
  For `EYE.RES`, 2,399,876 bytes (35%) are not covered by any directory entry, yet `lost_space=0`.
  The gaps are 5 runs, each right after a directory block. Each run walks cleanly as a chain of
  12-byte entry headers: 109, 128, 78, 1 and 1 entries.
- These look like older versions of the same slots: block 1's slots are 368/259/124/165 B in the gap
  against 372/268/147/184 B for the indexed copies, and 50 of block 2's 128 slots are >=90%
  byte-identical.
- **Verdict.** The walker counts are fine, but there was no tiling check; the claim is overstated.
- **Fix.** Document the stale region and warn against any raw byte-scan census of `EYE.RES`.
