# Eye of the Beholder 1 (DOS and Amiga): gap audit, 2026-11-13

> Changes applied: [audit-2026-11-13-changes.md](audit-2026-11-13-changes.md)

Report-only audit, 2026-11-13. None of these corrections have been applied yet. It was run by an
independent codebreaker re-derivation over the Westwood/SSI family (own LCW, PAK and AESOP RES
parsers in fresh Python; kyralib and eotb3lib were not imported; current ScummVM master sources
were fetched for cross-references). This page carries the findings that touch EOB1. Sibling pages:
`docs/eotb2/audit-2026-11-13.md`, `docs/eotb3/audit-2026-11-13.md`,
`docs/dungeonhack/audit-2026-11-13.md`, `docs/landsoflore/audit-2026-11-13.md`.

## Summary verdict

- Containers, MAZ, VCN/VMP size tiling, INF cross-port agreement and decoration file tiling are
  solid.
- Wall-decoration rects are read as pixels but the format stores them in 8-pixel columns. Every wall
  decoration in the EOB1-Amiga walker is drawn at one-eighth of its width from the wrong source
  column. This is the headline, and cheap to fix.
- Several smaller doc claims are wrong (VMP "identical across wall sets", the `skip=true` prefix
  theory, the INF layout row) and the Amiga palette sections contradict themselves.
- Biggest risk: the "pixel-exact" decoration verification is circular and has been trusted.

## Claims confirmed

| Claim | Evidence the audit used |
|---|---|
| EOB1 DOS PAK | 6 files and 193 directory entries (7 duplicate names inside `EOBDATA4.PAK` with identical bytes; `EOBPAL.COL` repeated across PAKs). Every file ends exactly on EOF once the last entry runs to EOF; consistent with the documented 185 unique entries. |
| MAZ | 4102 = 6 + 32x32x4 with header (32,32,4) for all 12 EOB1 levels (both ports). |
| VCN/VMP | EOB1 DOS 4bpp and EOB1 Amiga raw 5bpp at `0x22+40n`: decompressed sizes tile exactly; VMP max tile index = `numTiles-1`. EOB1 Amiga VMP is big-endian (count 2916 BE). |
| `.INF` | DOS and Amiga decompress and parse to identical headers, monster slots and wall/decoration record streams for all 12 levels. A real cross-port oracle, stronger than the prior "no out-of-range read" check. |
| `ITEM.DAT` / `ITEMTYPE.DAT` | EOB1 is the same as EOB2 apart from 4 item records with real data differences; this upgrades the EOB1 DOS doc's "hypothesis" field layout to confirmed. |
| Decoration `.DAT` files | All tile to EOF with 0 residue, max shape index = rect count - 1, flags take only {0,1,4,5} (the bit-0x02 census of 0/198 holds). |
| `resetWallData` defaults | `{1:1, 2:2, 3..22:3, 23:4, 24:5}` match `scene_eob.cpp:542-548`. |
| Trailing MAZ data | None: 4102 = 6 + 4096 confirmed for all 27 levels across EOB1 and EOB2. |

## Claims wrong or overstated

### 1. WRONG: wall-decoration rects are read in pixels, but stored in 8-pixel columns

- **Docs/code say.** `tools/eotb/decode-decorations.ts:45`: "pixel coordinates into the paired
  decoration CPS's 320x200 canvas". `tools/eotb/renderer.ts:66-74`: "`rect.w` and the source's
  `shapeData[2]<<3` necessarily name the same real pixel width". Both renderers blit
  `rect.x, rect.y, rect.w, rect.h` straight from the sheet (`tools/eotb/renderer.ts:261,272,274`).
  The cited verification is "193 px, bbox (65,32)-(73,56), 9x25px" (`docs/eotb/amiga/data-structure.md`,
  "Decoration overlays").
- **Audit found.**
  - ScummVM: `Screen_EoB::encodeShape` (`graphics/screen_eob.cpp:629`) does
    `src = page + y*320 + (x << 3)` and uses `w <<= 3`. It is called with the raw rect at
    `scene_eob.cpp:508`.
  - Census across 11 files and 1,615 rects (the 5 EOB1 `.DAT` files plus 6 EOB2 `.DEC` files, DOS and
    Amiga): the maximum `x+w` is exactly 40 in 10 files and 39 in one. 40 is 320/8.
  - Packing: BRICK rects 0-2 are `(0,55,9,25)`, `(9,55,6,17)` and `(15,55,4,11)`, edge-to-edge in
    column units.
  - Coverage with null control (DOS VGA sheets, share of the sheet's opaque pixels covered by the
    rect union, 9 sheets): x8 columns 0.90-1.00; pixels (current code) 0.12-0.23; AZURE2 is the one
    exception under the pixel reading (0.74).
- **Verdict.** WRONG. The "pixel-exact" verification was circular: the "hand-computed expected
  placement" used the same pixel assumption, and a 9-pixel-wide bbox for `w=9` is the symptom of the
  bug, not confirmation.
- **Fix.** Multiply `x` and `w` by 8 in `decode-decorations.ts` (or at the blit). Add a
  `> **Correction:**` block in `eotb/amiga/data-structure.md` at "Wall Set DAT Files", "Decoration
  overlays" and the "Both roles" verification table. Add TODO row `eotb-dec-rect-units`. (EOB2
  `CRIMSON.DEC` rect #152 `(5,178,6,27)` runs past row 200 to y+h=205; handle defensively.)

### 2. WRONG: "VMP identical across all wall sets within each game (BRICK.VMP = BLUE.VMP)"

- **Docs say.** `docs/eotb/amiga/data-structure.md:367`.
- **Audit found.** All 20 `.VMP` files (EOB1 and EOB2, DOS and Amiga) have distinct md5 hashes. Pairs
  within a game share only 292-664 of 2,916 entries.
- **Fix.** Delete the sentence or add a correction block.

### 3. WRONG explanation: the DOS docs' `skip=true` "4-byte `fileData` prefix" theory

- **Docs say.** `docs/eotb/dosvga/data-structure.md`, VCN section (~l.395) and INF section (~l.493).
- **Audit found.** `Screen_EoB::loadBitmap` (`screen_eob.cpp:405-470`) overrides the base version and
  calls `Screen::loadBitmap(filename, ..., pal)` without passing `skip`. In EOB, `skip` only
  suppresses the Amiga palette and PC98 planar post-processing. There is no prefix. Parsing at offset
  0 is right; the stated reason is wrong.
- **Fix.** Replace the theory with this source citation in both sections.

### 4. Contradiction inside the EOB1 Amiga palette sections

- `amiga/data-structure.md` ~l.150 still says each `.VCN` carries a "32-color palette at offset 0x40
  as 24-bit RGB". The VCN section (~l.339) supersedes this with no correction block at the old text.
- The VCN section also says the base palette is "the wall-set's `.PAL`", but EOB1 Amiga ships no
  `.PAL` files. The code uses `INVENT.CPS`'s embedded 40064-byte palette instead
  (`tools/eotb/export-dungeon.ts:34`). That base is well supported: `INVENT.CPS` slots 1-5 equal
  `BRICK.VCN`'s 5 colours exactly, so it was captured with a brick level loaded; `CHARGEN` and `TUNNEL`
  agree with `INVENT` on 26/26 of slots 6-31.
- Minor: `tools/eotb/palette.ts:13` says it is NOT `nibble*17`, but `round((n*63/15)*(255/63))` equals
  `n*17` exactly. ScummVM truncates to 6 bits first, giving 134 for nibble 8 against our 136; the
  difference is at most 3 per channel.
- **Fix.** Add correction blocks and document the INVENT-base mechanism with this evidence.

### 5. Cross-port difference not documented: `LEVEL3.MAZ` cell (4,30)

The DOS and Amiga files differ in 2 bytes: sides E/W are 13/18 on DOS and 3/8 on Amiga. Both fall in
the default 3..22 door range, so the VMP is the same, but the door shape set differs (`_wllShapeMap`
has -1 for 3-7 and 13-17). The other 11 levels are byte-identical across ports. Add one line in the
DOS MAZ section.

### 6. Minor doc errors

- The EOB1 Amiga INF layout table says "1 unused discriminator byte + `num`". The code
  (`decode-inf.ts:178-183`, net `pos -= 1; pos += 1`) has no extra byte, and that is correct: with the
  extra byte the parse runs off the end of the buffer. Fix the table row in `amiga/data-structure.md`
  section "Decompressed field layout".
- `amiga/data-structure.md` section "MAZ ... Additional Data" still lists "door state sequences /
  stair connections / event scripts" after the grid; there is zero trailing data.
