# Might & Magic II (Amiga + DOS): codebreaker gap audit, 2026-11-13

Report-only audit, 2026-11-13. None of these corrections have been applied yet.
Run by an independent codebreaker re-derivation of the MM1, MM2 and MM3 data and walker claims. Outside
oracles fetched for it: ScummVM `engines/mm/mm1` and Vairn/MM2 (`21-map-dat-format.md`,
`tools/mm2_map_move.py`, `game/src/gameplay/Movement.cpp`, `EXTRACTED/decomp/mm2_map_codec.h`,
`mm2_attrib_codec.c`). Shared findings are repeated so the page stands alone. Sister pages:
`docs/mm1/audit-2026-11-13.md`, `docs/mm3/audit-2026-11-13.md`.

## Summary verdict

- The MM2 map and attrib data decodes are solid (walls symmetric on 100% of indoor screens; DOS `MAP.DAT`
  decodes byte-exact to Amiga `map.dat` on 60/60 screens).
- The MM2 walker is wrong in ways the user would notice: **overland blocks 41.2% of moves the game
  allows**, because it uses Vairn's tools-level "Fallback" rule instead of the game's `0x9424`
  terrain check.
- The walker also checks the destination cell's back wall (0.9% of indoor moves wrongly blocked), starts
  from a heuristic cell (57/60 differ from `entry_coord`), and uses a hard-coded environment table
  instead of `attrib.dat` (screens 41-44 mislabelled overland).
- The N/E/S/W labels in the MM2 docs and codec are a permutation of the real layout.
- Biggest risk: `0x9424` was taken on trust from Vairn's ASM-cited code; the Amiga `mm2` executable was
  not re-disassembled.

## Claims confirmed

- **MM2 `map.dat`:** same row-major layout as MM1; walls symmetric on 100% of indoor screens. 2,730/2,730
  `event.dat` triplets sit on cells with collision bit `0x80` set (554 `0x80` cells have no triplet).
  Matches DOS `MAP.DAT` byte-exact on 60/60 screens.
- **MM2 `attrib.dat` neighbours:** all 24 overland screens fully reciprocal; interior screens point to
  themselves.
- **DOS `ATTRIB.DAT` 3840/3840 and `MONSTERS.DAT` 6656/6656** re-confirmed byte-exact with the Amiga files.
- **Frustum engine orientation and `movementBlocked`'s current-cell bit:** match ScummVM DIRMASK / `0x55`.
- **Bit-label correction spot-checked in the main session:** wall-bit labels are W,S,E,N (97% vs 37%
  agreement).

## Claims wrong or overstated

### 1. WRONG for MM2 overland: the walker's terrain blocking rule
- **Walker:** `tools/walker-mm/maze3d.ts:103-106` blocks if `(destV & 0x60) == 0x60 || destV & 0x80`.
  Vairn's `tools/mm2_map_move.py` labels this rule `# Fallback`; his ASM-cited version is
  `Movement.cpp` `passabilityObstruction` @ `0x9424`.
- **Game, per Vairn's ASM-cited code:** the move is open whenever the current cell's collision bit for
  that facing is clear. When set on overland, the game classifies the forward cell's terrain, then the
  current cell's, through a 32-entry `kClass` table (`visual & 0x1F`). Class 1/3 blocks unless the party
  has Mountaineering or Pathfinder (count >= 2). Class 4 blocks only when `surface & 0x0F == 0x0A`. Any
  other class lets the move through.
- **Measured** over all 23,040 interior overland moves, for a party with no skills: the walker blocks
  **9,490 moves (41.2%) that the game allows**; the reverse never happens.
- **Caveat:** Vairn's `0x9424` reading was taken on trust; the Amiga `mm2` executable was not
  re-disassembled.
- **Fix:** port `passabilityObstruction` and the `kClass` table; add a TODO row to verify `0x9424` /
  `A4-$720A` directly in the 68k code.

### 2. WRONG: the walker also checks the destination cell's back wall
- `maze3d.ts:100-102` (from `mm2_map_move.py`). The real check looks only at the current cell: MM2 (Vairn
  `0x9424`) `mm2_map_passability_blocked(coll_current, facing)`.
- The data really is asymmetric: 160 MM2 door faces are open on one side only, matching ScummVM's
  `Map::unlockDoor` toggling the current cell's bit.
- **Effect:** MM2 walker blocks 305 of 34,560 indoor moves (0.9%) the game allows; no cases the other way.
- **Fix:** drop the back-face check; document the current-cell-only rule as confirmed.

### 3. OVERSTATED: "MM1 and MM2 share this frustum math"
- `maze3d.ts:1-8`, `tools/walker/games-mm.ts:5-8`. ScummVM's MM1 `drawScene` differs from the MM2 engine
  (4-depth walk, neighbour walls as crops of the front tile, different x positions, nothing drawn in
  darkness). The primary impact is on MM1; MM2's geometry is the one the walker was written for. See the
  MM1 page, finding 4.

### 4. WRONG: start positions
- **Audit found:** `attrib.dat +0x0E entry_coord` is ASM-confirmed in Vairn's doc but the walker ignores
  it. It differs from the walker's start on 57/60 screens (e.g. screen 0 is (7,5) versus the walker's
  (1,1)).
- **Fix:** start from `entry_coord`.

### 5. WRONG in docs and codecs, harmless in the walker: N/E/S/W bit labels for map pages 0 and 1
- **Docs say:** `N = byte&3, E = >>2, S = >>4, W = >>6`; "West has no dark slot; 0x80 = event":
  `docs/mm2/amiga/data-structure.md:321-341`, `tools/mm2/map.ts:8-18` and `:43-58`. Labels come from
  Vairn's prose (`21-map-dat-format.md`), so "verified-real" means it matched his prose.
- **Symmetry check:** MM2 indoor screens 100% on every screen with the correct pairing; the doc's labels
  pair the wrong slots and score about 30%.
- **Actual layout:** **bits 0-1 W, 2-3 S, 4-5 E, 6-7 N**, y+1 = north, `idx = y*16+x`. Confirmed by
  ScummVM (`DIRMASK_N = 0xC0, E = 0x30, S = 0x0C, W = 0x03`) and by Vairn's decomp
  (`mm2_map_facing_shift` gives N = 6; comment: facing "N actually reads the file's WEST slot"). MM3 maze
  nibbles use the same order.
- **Collision page:** wall bits `0x55` & dirmask (N 0x40, E 0x10, S 0x04, W 0x01); `0x20` cell-level dark
  (`btst #5` @ `0x53DC`); `0x80` special/event; `0x02` and `0x08` unidentified.
- **Fix:** relabel decoded fields; `> Correction:` blocks in the doc and codec; make `dark` the `0x20` bit;
  add a TODO row for `0x02`/`0x08`.

### 6. WRONG/UNTRACKED: MM2 walker environment is a hard-coded range table instead of `attrib.dat`
- **Walker:** `games-mm.ts:178-184` treats screens 41-44 as overland.
- **Audit found:** `attrib.dat` gives them category 8/5/7/6, tileset 0, `surface = 0`, pointing to
  themselves on all four sides, every cell nonzero (they look like the elemental planes). Vairn defines
  overland as `surface_flag != 0`, which matches screens 5-16 and 33-40 only, so 41-44 get the outdoor
  renderer and terrain rule wrongly. Screens 45-54 have tileset `0x53` ("dungeon") but are drawn with
  `castle`; screen 52 has `0x33`.
- **Doc overstated:** `docs/mm2/amiga/data-structure.md:352` says "map_category (1 town, 2 cavern, 3
  dungeon, 4 castle) confirmed". In the data, overland screens use 1/2 and screens 41-44 use 5-8.
- **Fix:** drive environment from `surface` and `tileset_id`; add a TODO row for category 5-8 and tileset
  -> sheet.

### 7. WRONG (stale), and a cheap cross-version oracle: DOS `MAP.DAT` "unclassified"
- **Docs say:** `docs/mm2/dosega/data-structure.md:17` and `:123`.
- **Audit found:** a table of 60 `u16` LE offsets, then per screen a `u32` size (always 512) followed by
  LZW using the existing `lzwDecompress`. It decodes **60/60 screens byte-exact to Amiga `map.dat`**, so
  the Amiga grid is confirmed against a second port with no per-port reorientation.
- `EVENTSI.DAT` starts with what looks like the same shape: a 71 x `u32` offset table (first value
  `0x11C` = 284). Cheap to try next.
- **Smaller overstatement, line 14:** `STR.DAT` matches "byte-exact, full length". It matches only the first
  7,707 bytes; Amiga `str.dat` is 7,808 bytes, a prefix match.

## Unverified / open

- Vairn's `0x9424` / `A4-$720A` terrain rule against the Amiga 68k code (finding 1).
- Meaning of collision bits `0x02`/`0x08`; category 5-8 and tileset -> sheet mapping.
- `EVENTSI`/`EVENTSO`/`SPELLS.DAT` offset-table+LZW shape (untried).

## Recommended corrections (cheapest and highest value first)

1. Remove the back-face check; document the current-cell-only rule (finding 2).
2. Port `passabilityObstruction` and `kClass` (finding 1); verify `0x9424` in the Amiga binary.
3. Use `entry_coord` for starts (finding 4).
4. Relabel the bit layout and dark flag (finding 5).
5. Drive MM2 environment from `attrib.dat` (finding 6).
6. Promote DOS `MAP.DAT` as solved and fix `STR.DAT` wording (finding 7).
7. TODO rows: `mm2-overland-passability-0x9424`, `mm-walker-backface-check`, `mm-start-positions`,
   `mm-map-dir-labels`, `mm-coll-bits-0x02-0x08`, `mm2-env-from-attrib`, `mm2-dos-map-dat`.
