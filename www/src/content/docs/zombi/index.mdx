Zombi is the 1990 Amiga conversion, published by Ubi Soft, of a 1986 zombie-mall
adventure. It is the odd one out among the crawlers on this site. It has no wall
mosaic and no depth slots. Each of its locations is **one pre-drawn 160×80
picture**, and the map is a list of locations that each store their own exits.

This page summarises the raw notes in
[`docs/zombi/`](https://github.com/Shaid/crawl/blob/main/docs/zombi/). If this
page and those notes disagree, the notes are right. The research is one recon
pass plus one extraction commit, both dated 2026-11-21. The map, the picture
format, the sounds and the location-to-picture table are solved. The object
layer is not.

> **Before you write a decoder:** the `.seq` art is **Atari ST Cyber Paint**
> data, shipped to the Amiga unconverted. Its compressed frames are stored
> **column-major, plane-major** (`col = plane × wordsWide + x`). Reading them
> plane-interleaved gives pictures you can recognise but that are shredded.
> Its *raw* frames are the opposite: ordinary ST screen words, row-major.
> Palettes need a ×2 per channel before they match what the Amiga shows. See
> [Pitfalls](#pitfalls-and-corrections).

## The two walker answers

### Wall storage: per-cell (confidence: structural)

The map is split into two files:

- **`plan`** (336 B = 6 floors × 56 B) places the locations. Each floor is 7 rows
  × 8 columns, one byte per cell, and `0` means no location. Ids 1–86 each
  appear exactly once. Row 0 of every floor is empty.
- **`i-lieux`** (4,500 B = 90 × 50 B) holds the locations. Record `i` describes
  id `i+1`. Bytes 0–3 are its four horizontal exits and bytes 4–5 its two
  vertical exits. Ids 87–90 are not in `plan`. Their pictures are vehicle
  views.

Exit values: `00` open (120 faces), `14` open, door-like (42), `0A` blocked
(151), `FE` map edge facing outdoors (27). Four one-off values remain: `F0` ×2
on ids 36/39, `FA` on id 46 and `1E` on id 59.

Bytes 0, 1, 2, 3 lead to the plan cells (row+1, col), (row, col+1),
(row−1, col) and (row, col−1). The evidence:

- **162/162** open exits (`00` or `14`) land on an occupied `plan` cell. In a
  shuffled-position null, 85–101 of 162 do.
- **162/162** open exits are matched by the neighbour, with the same value. In
  the null, 20–28 do.
- All **6/6** vertical links join cells at the same (row, col) on adjacent
  floors: 1↔18 at (5,1), plus the elevator shaft 25↔45↔57↔60↔61 at (4,5).
- Two adjacent cells are often separated by `0A` (34 walled faces between neighbours), so adjacency
  in `plan` does not mean you can pass. The exit byte decides.

So every location stores all four of its own faces, plus up and down. This
converts straight into the `@seer-project/dungeon` per-cell model. Up/down
exits are a new requirement for that schema, which Hired Guns shares
([walker map-format decision, addendum 2026-11-21](https://github.com/Shaid/crawl/blob/main/docs/walker-map-format-future-decision.md)).
Which compass names apply is **not yet known**. If `plan` rows count upward,
the order is N, E, S, W. If they count downward, it is S, E, N, W.

### Renderer: one pre-drawn picture per location (confidence: confirmed from code)

This is a renderer shape new to the corpus. There are no per-facing views: a
picture per facing would need 86 × 4 = 344 frames, and `LIEUX.SEQ` holds 82.
The executable chooses the picture like this:

1. `LAB_0139` (`zombi` S_0 `+0x2B72`) opens `lieux.seq` and loads frame `n−1`
   for a 1-based picture number `n`.
2. `LAB_0275` (`+0x5088`) builds `n` from the location id. An 18-entry table at
   `+0x50B4` maps the outdoor car park onto shared pictures: 71→`0x46`;
   72–74→`0x47`; 75, 76→`0x48`; 77–81→`0x49`; 82–86→`0x4A`. Ids 87–89 map to
   `0x4B` and id 90 to `0x4C` (`+0x5F4A`..`+0x5F7A`).
3. A non-zero `i-lieux` byte 9 overrides the result (`LAB_0284`, `+0x51C8`).
   This is the `0x4D` on ids 72, 77 and 82.

The result covers 90 ids using 77 distinct frames
(exported as `public/assets/zombi/amiga/data/location-pictures.json`, `frames[id−1]`).
24 car-park cells share 12 pictures. This has not yet been checked against live
play. A Zombi walker is therefore a picture viewer with compass exits, not a
frustum renderer. Objects and zombies are presumably blitted over the picture
(open: `zombi-objects`).

## Headline findings

**The map: 86 locations on 6 floors.**

| Floor (`plan` bytes) | Ids | Pictures show |
|---|---|---|
| 0 (`0x00`–`0x37`) | 1–17 | brick service corridors and the basement (id 1 is a room with a staircase) |
| 1 (`0x38`–`0x6F`) | 18–34, 63–86 | mall ground level (18–34) and the outdoor car-park ring (63–86) |
| 2 (`0x70`–`0xA7`) | 35–47 | mall level ("Niveau 1/2" escalators) |
| 3 (`0xA8`–`0xDF`) | 48–58 | upper mall level |
| 4 (`0xE0`–`0x117`) | 59, 60 | escalator top / landing |
| 5 (`0x118`–`0x14F`) | 61, 62 | terrace and helicopter (roof) |

The "pictures show" column comes from reading the rendered frames, and assumes
frame ≈ id−1. The picture map above refines that assumption for ids 71–90.

**The Cyber Paint SEQ format.** All 11 files share one 128-byte file header:
`+0` magic `0xFEDB`, `+4` u32 frame count, `+8` speed. A u32 table of absolute
frame offsets starts at `+0x80`. Each frame has a 128-byte header holding a
16-word ST palette (`+4`), a 12-byte name (`+0x24`), x/y/width/height
(`+0x36`..`+0x3C`) and a storage byte at `+0x3F` (0 raw, 1 compressed). The
compressed stream is made of word tokens. If `c & 0x8000` is set, copy
`c & 0x7FFF` literal words. Otherwise, repeat the next word `c` times.

Verification, from `tools/shared/cyberpaint-seq.ts` and its test:

- Every compressed frame decodes to exactly `4·ceil(w/16)·h` words and uses up
  every input byte: 0 failures over the 191 compressed frames. In all there are
  210 frames: LIEUX 82, objet 67, z 22, skins 22, tetes 11, and six single
  pictures.
- Raw frames match `ceil(w/16)·h·8` bytes exactly (14 in `objet.seq`, 5 in
  `tetes.seq`).
- Null control: starting the stream 2 bytes late fails on **191/191**
  compressed frames.
- Each frame's stored length equals the gap to the next offset (LIEUX 81/81).
  The last frame is followed by 26 bytes of file padding.

**Sound effects.** Each `.SON` file is a `+0` u32 BE sample count (= file size −
6, 21/21) and a `+4` u16 BE rate (3,700–9,900 Hz), followed by signed 8-bit
PCM. The exporter writes all 21 as WAVs.

## Pitfalls and corrections

- **Palette scaling was wrong at first, and has been corrected (2026-11-21).**
  The first provisional mapping scaled each 3-bit ST channel by 36. Wrong for
  the Amiga. The executable stores the 16-word palettes of `PRESENT.SEQ` and
  `SCREEN.SEQ` (and of `echec`/`victoire`, except entry 0) with each 3-bit
  channel **doubled** (`n → 2n`, so ST `777` becomes Amiga `EEE`). An exact
  32-byte search finds the doubled words near `zombi+0x13BB8` and never finds
  the raw ST words. Exported colours are `2n × 17`. The location and sprite
  files use an ST palette whose entry 0 is `222` (Amiga `444`), not `SCREEN`'s
  `111`.
- **Column order.** Compressed SEQ frames are column-major in plane-major order.
  The plane-interleaved order (`x·4+plane`) gives recognisable but shredded
  pictures. That shredded output was the null that ruled it out.
- **Raw frames are not column-major.** The 5 raw `tetes.seq` heads and 14 raw
  `objet.seq` frames are ST screen words: row-major, with 4 interleaved plane
  words per 16 px. Read column-major, they are noise.
- **There are 11 `.seq` files, not 12.** The recon notes and plan counted 12.
  The extraction pass found 11 in the retail data.
- **Adjacency ≠ passage.** 34 faces between neighbouring cells are walled (`0A`). A walker
  that infers exits from `plan` alone opens shop walls.

## Reproduce

`npm run zombi:export` (= `npx tsx tools/zombi/amiga/export-data.ts
data/zombi/amiga/data`) writes `sprites/{lieux,objet,z,skins,tetes}`,
`screens/{present,screen,mask,button,echec,victoire}`, `palettes/*.json`, 21
WAVs and `data/{location-pictures,sounds}.json` to `public/assets/zombi/amiga/`.
The decoder, `tools/shared/cyberpaint-seq.ts`, works on any Cyber Paint file.
