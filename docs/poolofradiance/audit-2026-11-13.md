# Pool of Radiance (Amiga): gap audit, 2026-11-13

Report-only audit, 2026-11-13. None of these corrections have been applied yet. It was run by an
independent codebreaker re-derivation (own parsers and decoders written from the format spec, plus
read-only use of the repo decoders) over the four Gold Box Forgotten Realms titles; this page
carries the findings that touch Pool of Radiance. Sibling pages:
`docs/curseoftheazurebonds/audit-2026-11-13.md`, `docs/secretofthesilverblades/audit-2026-11-13.md`,
`docs/poolsofdarkness/audit-2026-11-13.md`.

## Summary verdict

- The containers, codecs, GEO grid and WALLDEF geometry hold up. The `.dax` container chains
  843/843 entries, and the codec passes the checksum on 843/843.
- The 8x8 tile pixel format is wrong. Every shipped PoR wall texture (`walldef*-view6.png`, 105 of
  them) is wrong pixels, and so are the walker's wall textures.
- Three open TODO rows (`por-pic-format`, `por-dungcom-semantics`, `por-8x8d-header`) rest on a wrong
  premise. One grammar covers all 511 image-class entries in 16 `.dax` files with zero remainder.
- Palettes are not tracked anywhere. PoR's `.dax` files are 4bpp with no palette, so it is
  probably in `program`.
- Biggest risk: the "visual confirmations" of the 1bpp decode in the docs are plausibility checks of
  a wrong decode, so they are circular.

## Claims wrong or overstated

### 1. WRONG: the 8x8 "1bpp, 8 bytes per tile" format (highest impact)

- **Docs say.** Tiles are header-less 1bpp MSB-first 8-byte tiles, and one walldef byte indexes one
  tile: `goldbox-glib-format.md:336` (Render row) and section 5.7 (:360-390); PoR `data-structure.md`
  section 3 (lines 225-241, "visual evidence" 259-282). Code: `tools/shared/goldbox-walltiles.ts:93`
  (`decode8x8Tiles`) and `tools/poolofradiance/amiga/walldef.ts:114` (skips 4 bytes).
- **Audit found.** `8x8d.dax` entries have a 12-byte header:
  `u16 h=8, u16 wBytes=2, u16 x, u16 y, u16 count, u16 bytesPerPlanePerItem=16`. It is followed by
  4 planes, each plane holding the whole bank. Each item is 16x8 pixels, i.e. two glyphs. All 23/23
  entries satisfy `len == 12 + count*16*4` exactly. The shipped decoder therefore starts 8 bytes too
  early and reads single bitplanes as if they were tiles.
- **Index mapping.** Index 0 = none, 1-45 = universal glyphs 0-44, then 46 + 70*slot + k for the
  wallset slots. PoR's own `program+0x6D53E` holds `0001 002E 0074 00BA 0100`, the symbol_set_fix
  table, which says exactly this. PoR's universal bank has 46 glyphs; glyph 45 is all-zero padding
  that fills out the last 16-wide item.
- **Evidence.**
  - Seam-continuity oracle (colour agreement across adjacent glyph edges in all 10 views, against a
    random-pair null; lift = (observed - null)/(1 - null)): PoR, corrected decode with the blank+45
    alignment, lift 0.46; the other alignments score 0.29 and 0.31. (Family reference, Curse:
    corrected 0.584 vs null 0.201, lift 0.48; shipped 1bpp reading 0.655 vs null 0.621, lift 0.09.)
  - Cross-title oracle: 31/45 PoR universal glyphs have the same colour partition as Curse's
    universal glyph at the same index. Under the shipped reading, only 1 of 122 PoR tiles matches any
    Curse glyph in any position.
  - ASCII render with the corrected decode: PoR wall 1 shows as bevelled masonry.
- **Consequences.** The docs' "crenellation / door / herringbone" confirmations are circular.
  Section 5.6's correction ("one byte = one block, CONFIRMED") was never propagated to the code:
  `goldbox-walltiles.ts` still indexes 8-byte tiles and its module doc (~line 66) still says the
  question is open.
- **Fix.** Replace `decode8x8Tiles` with a glyph decoder for this grammar and rebuild the bank as
  [none, U0..U44, slot glyphs]. Re-render, using the seam and cross-title oracles as the regression
  check. Add TODO row `goldbox-glyph-format`.

### 2. WRONG / cheaply closable: `por-pic-format`, `por-dungcom-semantics`, `por-8x8d-header`

- **Docs say.** PoR `TODO.md:578-580`, with the claims in `data-structure.md` section 4 (286-327)
  and section 5: `pic.dax` matches no known picture format, a "vector draw-command" lead, a 4-byte
  8x8d header of unknown meaning, and dungcom "not a multiple of 8".
- **Audit found.** One grammar covers all 511 image-class entries in 16 `.dax` files, zero
  remainder:
  - an image is the 12-byte header `(h, wBytes, x, y, count, bpi = h*even(wBytes))` followed by
    `bpi x 4 planes x count`;
  - an animation is `u16 0, u16 frames`, then per frame `u32 delay` plus one image.
  - Fits: 8x8d 23/23, pic 59/59, cpic 118/118, sprit 55/55, cbody 128/128, head 39/39, body 21/21,
    chead 28/28, comspr 25/25, final 3/3, icon 6/6; dungcom, wildcom, randcom, bacpac and sqrpaci
    also fit.
  - `pic.dax` holds animated 88x88 4bpp pictures; entry 0 renders as a horned monster portrait
    (`pic0.png`). `dungcom.dax` is 13 frames of 48x24 at 4bpp: 12 + 13*144*4 = 7,500 bytes, exactly
    the entry size.
  - The section 4 Gold Box Explorer negative came from the animation wrapper's leading `u16 0`, not
    from an unknown format.
- **Fix.** Rows become "structure confirmed (511/511), palette open". Write a PoR image/animation
  decoder; propose row `por-image-grammar`, which closes all three.

### 3. OVERSTATED: ECL wallset-binding coverage

- **Docs say.** PoR `data-structure.md:385` and `:409-417`: "26/29 ... every one fully", "5/7 DO
  resolve". (Family-wide, GLIB `:681-691` and `:860-869`: "every level that resolves at all
  resolves ALL 3 slots".)
- **Audit found.** Checking the shipped bindings in the `level-*.json` outputs against the slots the
  GEO grid actually uses: PoR level 0 and level 7 both bind to `(127,127,127)`, the "don't touch"
  placeholder, yet level 0 uses slots 0-2 and level 7 uses slots 0-1. So PoR really has 24/29 levels
  with working bindings, and level 7's NEWECL chase "resolves" only to placeholders.
- **Hypothesis (cheap to test).** Loading a multi-wallset WALLDEF entry fills the following slots
  too.
- **Fix.** Count 127/255 as unresolved; add row `goldbox-ecl-multiwallset-slotfill`.

### 4. Stale text and contradictions

- PoR intro (lines 3-8) says the three siblings were "not touched".
- PoR GEO planes 0/1 heading at `:361` still says "remain open, escalated", although a correction
  block sits under it.
- GLIB section 4 still mentions a "still-open per-wall-id tile-pixel-layout puzzle".
- Typo in the GLIB section 7.2 correction: PoR's denominator is given as "88/16,896"; the audit
  counts 88/29,696 (29 levels x 1024).
- Side note: PoR's GEO prefix `00 04` read little-endian is 1024, the record length, so it is
  probably a length field rather than a "constant tag". The ECL prefix `88 13` read little-endian is
  5000.

### 5. GEO verification numbers do not reproduce (conclusion holds)

| Check | Audit | Documented |
|---|---|---|
| Plane 3 shared-wall agreement, horizontal/vertical (does the wall exist from both sides) | 99.5/99.5 | 95.3/95.4 |
| Planes 0/1 wall-type nibbles in documented N/E/S/W order | 96.1/95.9 | not stated here |

The best wrong ordering gets at most 0.57 on the vertical axis; it ties on the horizontal axis
because a N/S swap is invisible to a horizontal check. The documented "best of the other 23
permutations 55.7%" is not what a full scan gives. Replace the numbers with script-backed ones and
state which axis each permutation check can tell apart.

## Unverified / open

- **Palettes (untracked).** Nothing in the docs or code mentions a palette; all output is greyscale
  or 1bpp. PoR's `.dax` files are 4bpp with no palette, so it is probably in `program`. Add row
  `por-palette`.
- The audit did not re-check the Pools v1.3 opcode table, CFG-walk counts beyond the placeholder
  analysis, or the plane 2 meaning.
- Untracked unknown (shared with the GLIB titles): no row for sounds, strings, `.FON`, music, or
  items files; the `*-full-catalog` rows are too broad to drive work.

## Recommended corrections, cheapest/highest value first

1. Fix the glyph decoder (finding 1) and re-render the PoR wall sets with the seam and cross-title
   oracles as checks.
2. Write the PoR image/animation decoder (finding 2); closes three rows structurally.
3. Look for PoR's palette in `program` (`por-palette`).
4. Test the 127 slot-fill rule (finding 3) and count 127/255 as unresolved.
5. Fix the stale text and typo (finding 4); replace the GEO numbers (finding 5).
6. Add TODO rows: `goldbox-glyph-format`, `por-image-grammar`, `por-palette`,
   `goldbox-ecl-multiwallset-slotfill`.

## Process notes

- The 1bpp decode "renders coherently" because a single bitplane of a multi-plane glyph looks like
  plausible 1bpp art, so a coherence check cannot catch it. Seam continuity with a null, and
  cross-title agreement, can.
- A "CONFIRMED" correction in a doc needs a grep of the decoder that uses it: section 5.6 was
  confirmed but the code was never updated.
- TODO rows `por-pic-format` etc. should be closed or re-scoped rather than left as "unknown format".
