# Dungeon Hack (DOS VGA): gap audit, 2026-11-13

> Changes applied: [audit-2026-11-13-changes.md](audit-2026-11-13-changes.md)

Report-only audit, 2026-11-13. None of these corrections have been applied yet. It was run by an
independent codebreaker re-derivation over the Westwood/SSI family (own AESOP RES parser in fresh
Python; current ScummVM master sources were fetched for cross-references). Dungeon Hack received
little direct coverage; this page carries the findings that touch it. Sibling pages:
`docs/eotb/audit-2026-11-13.md`, `docs/eotb2/audit-2026-11-13.md`, `docs/eotb3/audit-2026-11-13.md`,
`docs/landsoflore/audit-2026-11-13.md`.

## Summary verdict

- The AESOP container for `HACK.RES` and `OPEN.RES` is solid: undirectoried bytes equal the header's
  `lost_space` exactly.
- One cross-reference claim is wrong: the EOB3 docs say the `ITEMTYPE.DAT` format applies to Dungeon
  Hack, but no `ITEMTYPE.DAT` exists in `data/dungeonhack`.
- Nothing else in the audit was directed at this title; absence of findings is not a clean bill of
  health.

## Claims confirmed

| Claim | Evidence the audit used |
|---|---|
| `HACK.RES` / `OPEN.RES` container | Bytes not covered by any directory entry equal the header's `lost_space` exactly: 45,816 and 12,588 respectively. A solid tiling result. |

## Claims wrong or overstated

### 1. WRONG (in EOB3 docs): "the same format applies to Dungeon Hack"

- **Where.** `docs/eotb3/itemtype-dat-offset-correction.md` states the `ITEMTYPE.DAT` format also
  applies to Dungeon Hack.
- **Audit found.** No `ITEMTYPE.DAT` exists in `data/dungeonhack`.
- **Fix.** Drop the Dungeon Hack claim from the EOB3 docs. (See
  `docs/eotb3/audit-2026-11-13.md` for the larger `ITEMTYPE.DAT` finding.)
