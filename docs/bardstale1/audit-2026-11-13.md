# Bard's Tale 1 (Amiga): codebreaker gap audit, 2026-11-13

Report-only audit, 2026-11-13. None of these corrections have been applied yet.
Run by an independent codebreaker re-derivation: the auditor wrote its own Python decoders (an
independent Huffman decoder and a stock Okumura LZHUF) and compared them against the TypeScript port.
The audit covered Bard's Tale 1-3 together; findings that are family-wide are repeated here so this
page stands alone. Sister pages: `docs/bardstale2/audit-2026-11-13.md`,
`docs/bardstale3/audit-2026-11-13.md`.

Data location used: `data/_unexplored_/BardsTaleNTSC/`. The slave identity strings check out for all
three games.

## Summary verdict

- The picture codec is correct. The independent Huffman decoder reproduces the TypeScript port byte for
  byte on BT1 55/55 (BT2 61/61 and BT3 84/84 on the sister pages).
- Two TODO rows (`bt1-unk-field`, `bt1-animation-overlay`) are open only because nobody decoded the
  field or the data after the RLE terminator. Both are answerable now.
- Almost every other BT1 data file uses the same `[u32 size][u32 bitcount][Huffman]` container, so the
  "unknown banks" are one shared codec away from decoded.
- **No map, wall or door encoding is claimed anywhere in the BT docs**, so there was nothing on that
  front to audit. It is untracked (finding 7 below), and it is the obvious next pass.
- Biggest risk: the doc claims "cmp-identical to Kroah's `Files/`" and "visually cross-checked against
  Kroah's gallery" cannot be re-run (no copy on disk).

## Claims confirmed

- Game identity from the slave strings (3/3 games).
- BT1 RLE plus 112x88 4bpp plane-major picture. The independent decoder matches 55/55. A row-interleaved
  null control renders as noise, and no palette word is above 0x0FFF.
- BT1 `pics` record 54 needs 1 byte past EOF, but this only changes the RLE terminator byte: 0 of 4,928
  pixel bytes differ.
- The codec is stock Okumura LZHUF where it applies (BT3), which gives a third-party oracle for the
  shared Huffman/LZHUF code (see finding 10 on the BT3 page).

## Claims wrong or overstated

### 1. WRONG: "`unk` field is always `0x167B6`, role unknown"
- **Docs say:** `docs/bardstale-picture-format.md:64,256-257`; codec line 616; TODO rows
  `bt1-unk-field` / `bt2-unk-field`.
- **Audit found:** `unk` is the exact number of bits in the Huffman stream (tree + palette + payload).
  BT1 `pics`: big-endian, exact match on 54/55. The odd one is record 54, the last in the file, which
  needs 1 byte past EOF; with 2 bytes of padding it matches exactly. `0x167B6` never appears in our
  data. This also gives the Huffman tree decoder an independent zero-deviation check.
- **Fix:** document the field, add it as a sanity check in the decoder, and close `bt1-unk-field`.

### 2. UNTRACKED / OVERSTATED: BT1 records hold animation data that is decoded and then thrown away
- **Docs say:** `sizeDst` is "32 (palette) + payload", with a garbled example (`picture-format.md:63`);
  `bt1-animation-overlay` asks whether such data exists.
- **Audit found:** in 44/55 BT1 records the Huffman output continues after the RLE terminator, 185,308
  bytes in total. The format is structured: u16 count, then entries of the form `03f0 0200 ...`
  ending in `ffff`.
- **Fix:** answer `bt1-animation-overlay` (yes, it is inline in the payload), add a `bt1-animation-format`
  row, and fix the `sizeDst` text.

### 3. UNTRACKED, high value: every BT1 data file uses the same `[u32 size][u32 bitcount][Huffman]` container
- The existing codec decodes every BT1 data file, and the bit-count rule from finding 1 holds with zero
  deviation (exact big-endian on BT1).
- 40/40 single-record files across BT1 and BT2 (BT1 members: `big_city`, `big_dung`, `dung_blank`,
  `bard_screen`, `control_panel`, `icon0-4`, all 5 instruments, `title`, `CITY/bi1...BI9`, `city.name`,
  `city.path`).
- Directory file: BT1 `levs` (16 x 2,048 B).
- Decoded payloads: BT1 `levs` record 0 starts with 484 = 22x22 bytes of 2-bits-per-side wall data
  (`05`/`50`/`44` patterns), then a 484-byte flag grid. The record's slack holds leftover Applesoft
  BASIC source text ("SET CONSTANTS FOR LOOP -- S9 IS SIZE OF EACH VOLUME"). The instrument files
  decode to signed 8-bit PCM (`chant` lag-1 correlation 0.93).
- So `bt1-other-banks` and `bt1-audio` move from "codec unknown" to "interpret the decoded payload".
- The map, wall and door encoding is the obvious next pass, and no row tracks it today.

### 4. OVERSTATED: "no count field; counts must be found by decode-until-failure"
- **Docs say:** `picture-format.md:36-43,127-133`; BT2 TODO paths-tried (same claim).
- **Audit found:** the first directory offset divided by 4 gives the slot count directly: 220/4 = 55 for
  BT1 (256/4 = 64 for BT2, 344/4 = 86 for BT3). Records also run back to back up to EOF with the
  bit-count rule holding. The "not decisive" paths-tried entry is wrong; the directory scan was decisive.

### 6. UNVERIFIED: "Kroah's `Files/` are cmp-identical" and "visually cross-checked against Kroah's gallery"

### 7. Untracked inventory gaps and cross-title facts

- `chant`, `drums`, `harp`, `panflu`, `trumpet` and `dung_blank` are identical in BT1 and BT2, so
